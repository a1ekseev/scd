# Принятые решения по миграции на Go

Этот файл имеет приоритет над отчётами 01–06: где отчёт расходится с решением ниже, действует решение.

## D1. Стек — самый современный (2026-10-17)
- `go.mod`: `go 1.27.0`, `toolchain go1.27.2`; все зависимости — последних версий, без подбора под старый toolchain.
- CI: `actions/setup-go@v7` (`go-version-file: go.mod`), `go vet`, **golangci-lint v2.15.0** (`golangci/golangci-lint-action@v9`) — блокирующий шаг, без baseline; `govulncheck`; `go test -race`.
- Детали — `06-go-stack.md` §1, §11.

## D2. Приоритет — внутренняя функциональность работы с Xray API (2026-10-17)
Работа с Xray API — ядро сервиса; её поведение переносится строго:
- тот же набор RPC (HandlerService: List/Add/Remove Outbound/Inbound; RoutingService: ListRule/AddRule(shouldAppend=true)/RemoveRule);
- тот же порядок apply (outbound → inbound → routing), полная замена негенерированных ресурсов, сохранение `fixedOutbounds/fixedInbounds/fixedRouting`, rollback только для outbound, сохранение хэшей только при успехе всех kinds;
- те же сценарии repair / rejoin балансера в мониторинге, тот же per-target lock, те же таймауты и тексты ошибок;
- фиксировать поведение тестами против in-process фейкового gRPC-сервера (bufconn), повторяющего семантику Xray v26.3.27 (см. `02-scd-xray-api.md`).

Реализация: нативные пакеты `github.com/xtls/xray-core` (v1.260327.0) за одним внутренним интерфейсом `xrayapi.Client`, вместо ручного protobuf-энкодера.

Ошибки кодирования, найденные в TS (ws: `protocol_name` в поле 1 вместо 3 → теряются path/Host; TLS: fingerprint в поле 10 вместо 11), в Go **не переносятся**: типизированные сообщения xray-core кодируют поля корректно. Это намеренное отличие от TS-версии — цель «сохранить функциональность», а не повторить баг. **Подтверждено владельцем 2026-10-17.**

## D3. Status UI: стек HTML можно менять, визуально — как сейчас (2026-10-17)
- Байтовое совпадение HTML **не требуется**. Можно `html/template` + `embed`, другое экранирование (`&#39;` и т.п.), другая разметка внутри, если внешний вид тот же.
- Требование: дашборд визуально идентичен текущему — та же структура (instance → subscription → target, balancer-first блоки, карточки туннелей по latency), те же данные, цвета, статусы, тексты.
- Проверка: снять эталонные скриншоты TS-дашборда (Playwright/Chromium) на фиксированных фикстурах состояния до удаления TS, затем сравнивать скриншоты Go-версии (visual regression) вместо golden-файлов HTML.
- JSON API (`/api/status`, `/api/instance-status`, `/api/instances`, `/api/runtime-state`) остаётся контрактом: схемы и поля сохраняются, т.к. ими пользуются удалённые инстансы и автоматизация.

## D4. Целевая версия Xray — самый свежий релиз v26.10.10 (2026-10-17)
- v26.10.10 — **pre-release** (как и все 15 релизов после v26.3.27); тега `v1.261010.0` нет. Go-зависимость — псевдоверсия по коммиту: `github.com/xtls/xray-core v1.260327.1-0.20261010092107-701af60772cd` (`@latest` всё ещё даёт v1.260327.0 — Dependabot/Renovate для xray-core отключить, обновлять вручную вместе с compose; CI сверяет хэш коммита go.mod ↔ тег образа).
- xray-core требует `go 1.27` — совместимо с D1.
- gRPC-контракт scd (9 RPC, все используемые номера полей, тексты ошибок) на v26.10.10 не изменился — проверено вживую (08 §2–3).
- **TLS `allowInsecure` удалён из Xray** (с v26.6.22). Решение по нему — в рамках D11 (полная адаптация подписок под v26.10.10), см. `09-subscriptions-xray-26.10.10.md`. TLS в Xray теперь доверяет встроенному CA-bundle (опция `use_system_ca=23` не выставляется, как и раньше).
- Тестовый Xray в `docker-compose.yml`: `ghcr.io/xtls/xray-core:26.10.10`.
- Фейковый gRPC-сервер в тестах и все выводы `02-scd-xray-api.md` (номера полей, семантика RPC, ошибки) перепроверяются против v26.10.10 — результат в `08-xray-26.10.10.md`; где он расходится с 02, действует 08.
- Правило на будущее: версия xray-core в `go.mod` и образ Xray в compose обновляются вместе.

## D5. Разрешение конфликта 02 vs 06 по gRPC (2026-10-17)
`06-go-stack.md` §8/§13 предлагает портировать ручной protowire-энкодер, `02-scd-xray-api.md` — нативные пакеты xray-core. Действует D2: **нативные пакеты xray-core** (типизированные сообщения, корректные номера полей, меньше риск дрейфа при обновлении Xray). Цена — бинарь ~+8 МБ, принимается.

## Ответы владельца на открытые вопросы (2026-10-17)

## D6. Баги кодирования ws path/Host и TLS fingerprint — исправить
Go-версия кодирует поля корректно (типы xray-core). Тест: golden-проверка, что path/Host/fingerprint реально доходят до Xray.

## D7. Остановка — сразу и корректно
`signal.NotifyContext` (SIGINT/SIGTERM) → отмена `context` всех cron-циклов, мониторинга и HTTP-серверов (`http.Server.Shutdown` с таймаутом), дожидаемся текущих операций apply, выходим. Не повторяем: ожидание следующего cron-слота после SIGTERM (scd, sfc), переполнение таймеров >24.8 дней, зависание gtl при обрыве клиента (Go: `r.Context()` отменяется).

## D8. Регулярные выражения — стандартный Go `regexp` (RE2)
Владелец сам обновит регулярки в конфигах. Выбор: stdlib `regexp` — без зависимостей, линейное время (нет ReDoS на данных из подписок), идиоматично. `dlclark/regexp2` не используем.
- Формат в конфиге: строка-паттерн RE2; поддерживается литерал `/pattern/flags` с флагами `i`, `m`, `s` (→ `(?ims)`), прочие флаги (`g`, `y`, `u`, `d`, `v`) — ошибка валидации.
- Lookahead/lookbehind/backreferences → ошибка на `validate-config` с понятным текстом и путём поля.
- Сопоставление — `MatchString` (поиск подстроки, как JS `test` без `y`).
- Обновить README: примеры фильтров без lookahead (например, исключение через отдельный `labelExcludeRegex` — только если владелец попросит; по умолчанию просто переписать примеры).

## D9. Поведение по-Go, а не по-Node
Тексты ошибок (сетевых, валидации, разбора) — нативные Go; повторять Node-специфику (`fetch failed`, `User-Agent: node`, тексты zod, ICU-сортировка, lenient base64, WHATWG-нюансы URL) **не нужно**. Контрактом остаются: функциональность, JSON API status-сервера, внешний вид дашборда (D3), поведение по отношению к Xray (D2). Отчёты 01/03/04/05/06 в части «повторить Node 1:1» читать с поправкой: это список мест, где Go поведёт себя иначе, — каждое такое место решаем в пользу корректного/идиоматичного Go и фиксируем тестом, без побайтной эмуляции Node.
Следствия: `schema`-пакет без эмуляции текстов zod (свои понятные сообщения с путём поля); стандартный `encoding/base64` (с поддержкой обоих алфавитов и опционального padding); сортировка — `slices.Sort`/`strings.Compare`; разбор VLESS через `net/url` с явными правилами; логи — `log/slog` JSON/text без эмуляции pino (имена событий и поля сохраняются как `msg`/атрибуты).

## D10. Единый бинарник и единый образ — `scd`
- Нет имени `blanc`. Go-модуль `github.com/a1ekseev/scd`, бинарь `scd`, `cmd/scd/`.
- Один Docker-образ `ghcr.io/a1ekseev/scd`. Образы `sfc`/`gtl` больше не публикуются.
- CLI: команды scd на верхнем уровне без изменений (`scd sync|daemon|generate|validate-config|print-config`), остальные сервисы — подкоманды: `scd sfc serve|refresh|validate-config|…`, `scd gtl serve|validate-config|…` (точные подкоманды — как в текущих CLI sfc/gtl). Без multicall по argv[0].
- docker-compose: три сервиса на одном образе с разными `command:`. Образ по умолчанию: `CMD ["scd","daemon","--config","/app/config/config.yml"]`.
- CI publish: один образ (amd64+arm64), теги `latest` и semver.
- Пакеты `internal/{scd,sfc,gtl}` — как в 00-overview; корень модуля переименовывается в `scd`.

## D11. Подписки полностью адаптируются под Xray v26.10.10
Не только `allowInsecure`, а **все** параметры/профили VLESS-подписок приводятся к тому, что поддерживает и как трактует v26.10.10 (удалённые/переименованные поля, новые дефолты, валидация). Аудит каждого параметра и рекомендации — `09-subscriptions-xray-26.10.10.md`; где он расходится с 01/02, действует 09. Изменение хэшей/тегов после миграции допустимо, если оно следствие адаптации (однократный полный re-apply).

## D12. Тестовые конфиги
Временные secret-free конфиги: `docker/{scd,sfc,gtl}/config.example.yml` (tracked) + фикстура подписки с фейковыми ссылками `docker/fixtures/`; локальные `config.yml` (ignored) — копии. Владелец пришлёт реальные позже.

## Решения по аудиту подписок (`09-subscriptions-xray-26.10.10.md` §8), 2026-10-17

## D13. TypeScript-версию не трогаем
Hotfix падения Xray (REALITY без `spider_y`, 09 §1.4) в TS **не делается**. В Go `SpiderX`/`SpiderY` заполняются всегда; обязательный регрессионный тест.

## D14. Scope новых профилей: xhttp и постквантовое шифрование
К трём текущим профилям добавляются: транспорт **xhttp** (`type=xhttp`, `path`, `host`, `mode`, `extra`) и **VLESS-шифрование ML-KEM** (`encryption=mlkem768x25519plus.*`). Плюс параметры, которые реально приходят в ссылках и нужны для совместимости: `spx`, `pcs`, `vcn`, пустой `sid`. Остальное (grpc, httpupgrade, kcp, ech, finalmask, `pqv` и т.п.) — не в scope; ссылки с `ech`/`fm` и неподдерживаемым `encryption` **пропускаются** (skip с причиной), а не упрощаются молча.

## D15. `allowInsecure` — настройка в конфиге, по умолчанию запрещено
Новый ключ конфига (имя уточнить при реализации, напр. `subscriptions[].allowInsecure: deny|allow`, default `deny`).
- `deny` (по умолчанию): ссылка с `allowInsecure=1` без `pcs`/`vcn` → skip с причиной.
- `allow`: outbound создаётся (в Xray v26.10.10 поля нет — TLS всё равно проверяет сертификат), warning в лог.
Ссылки с `pcs`/`vcn` обрабатываются штатно (`pinnedPeerCertSha256` / `verifyPeerCertByName`).

## D16. `flow`
Пустой `flow` — норма. Если `flow` указан там, где Xray его не поддерживает (напр. `xtls-rprx-vision` на ws): flow сбрасывается в пустой, warning в лог (как 3x-ui). Набор допустимых `flow` и транспортов — по коду Xray v26.10.10.

## D17. Пустой `sid` — разрешён (по стандарту share-link; на работу не влияет).

## D18. id пользователя: без строгой UUID-проверки, но непустой
Любая непустая строка; приведение — как в Xray (UUID или строка → UUID через `uuid.ParseString`). Пустой id → skip.

## D19. Билдер — вариант B: JSON → `infra/conf` → gRPC API (2026-10-17)
Из ссылки строится outbound в форме JSON-конфига Xray v26.10.10 (тот же, что хэшируется в manifest), затем `conf.OutboundDetourConfig.Build()` превращает его в protobuf, и результат отправляется в Xray **через gRPC API** (`AddOutbound`). Требование владельца: все параметры ссылки должны доходить до Xray через API — golden/интеграционные тесты проверяют, что каждый поддерживаемый параметр (вкл. xhttp и ML-KEM, D14) присутствует в `ListOutbounds` живого Xray. Inbound (SOCKS) и routing-правила собираются так же через `infra/conf` (`InboundDetourConfig`, `RouterRule`), если это не усложняет код; иначе — типами xray-core напрямую. Бинарь ~35 МБ — принимается. Перекрывает D5 и рекомендацию A в 09 §3.4.

## D20. TypeScript удаляется полностью — последним шагом (2026-10-17)
Итог миграции — только Go-код. На последнем этапе удаляются целиком: `scd/`, `sfc/`, `gtl/` (src, test, package*.json, tsconfig*, Dockerfile'ы, .dockerignore), Node-шаги CI, любые упоминания npm/Node/TypeScript в README/AGENTS.md/docker-compose. Эталоны этапа 0 снимаются до удаления и хранятся как Go-testdata (без Node-скриптов в итоговом дереве).

## D21. Сдвиг портов туннелей — не проблема (2026-10-17)
SOCKS-порты туннелей — внутренние: их генерирует и использует сам scd для мониторинга каждого подключения, снаружи напрямую не используются. Перераспределение портов после миграции допустимо. Остаётся только проверка ёмкости `portRange` (ошибка с понятным текстом при переполнении).

## D22. Выбор балансера на дашборде — по рекомендациям `10-balancer-selection.md` (2026-10-17)
1. В набор RPC (D2) добавляются read-only `RoutingService.GetBalancerInfo` и `ObservatoryService.GetOutboundStatus`; в `docker/xray/config/01_api.json` включается `ObservatoryService`.
2. Опрос по умолчанию — каждые 15 с, отдельный read-only цикл без target-lock.
3. Для `random`/`roundRobin`/`leastLoad`-пула показываются стратегия и набор кандидатов.
4. Кнопки override в UI нет — дашборд только для чтения.
5. «Нет живых кандидатов → трафик в fallback/direct» отображается как degraded.
Тег балансера задаётся в конфиге target (Xray его через API не отдаёт). JSON API — только аддитивно, `version` снапшота не меняется. При выключенной функции дашборд как раньше (D3).

## D23. Технические решения, принятые без вопроса владельцу (2026-10-17)
Следуют из D7/D9 (поведение по-Go); закрывают «открытые решения» из 03 §11 и 08 §8.
- **Ошибка аллокации портов** (`preparePlanForTarget`) валит только свой target, а не весь sync (как остальные ошибки target'а).
- **Cron:** один парсер для валидации конфига и планировщика; 5 или 6 полей (секунды опционально), списки/диапазоны/шаги/имена, дескрипторы `@hourly`/`@daily`/…; без `L`/`W`/`#`. Часовой пояс — локальный процесса (в образе UTC). Неподдерживаемое выражение — ошибка `validate-config`. Библиотека выбирается на этапе 1 (кандидат — парсер `github.com/robfig/cron/v3` с `SecondOptional|Descriptor`), с тестами на выражения из примеров конфигов.
- **SOCKS/HTTP-проба:** один общий дедлайн на проверку через `context` (идиоматично для Go) вместо idle-таймаута на каждую фазу; latency — от отправки запроса до заголовков ответа (смысл метрики сохраняется).
- **Паника в HTTP-handler** → 500 и лог, процесс не падает.
- **Сортировка** имён на дашборде — `strings.Compare`/`slices.Sort` (без ICU-коллации).
- **JSON API** — порядок ключей задаётся порядком полей Go-структур; схема и имена полей сохраняются.
- **Известные ограничения Xray v26.10.10 — в README, без кода:** TLS доверяет встроенному CA-bundle (частные CA в образе не работают); SOCKS UDP ASSOCIATE на эфемерном порту (UDP через туннели снаружи Docker не работает, TCP и мониторинг не затронуты); `routing.script` (Lua) в статическом конфиге Xray перекрывает правила scd — не поддерживается.

## Ответы владельца после ревью плана (2026-10-17)

## D24. Cron — классический Linux-стиль
Формы `@minutely`/`@weekdays`/`@weekends`, dow `7`, `L/W/#/H`, пустое расписание в реальных конфигах **не используются** — поддерживать не нужно. Нужен привычный Linux crontab: 5 полей (`мин час день месяц день_недели`), списки, диапазоны, шаги, имена месяцев/дней, макросы `@yearly/@annually/@monthly/@weekly/@daily/@midnight/@hourly`. Дополнительно разрешается необязательное 6-е поле секунд впереди (нужно для частых циклов, напр. balancer selection 15 с, D22). Выражения, которые никогда не срабатывают, — ошибка валидации. Уточняет D23.

## D25. Текст причины для невалидного ключа ML-KEM: «Invalid VLESS encryption key.» — принято.

## D26. Максимальная совместимость с Xray — в рамках выбранного scope (уточнено владельцем 2026-10-17)
Scope транспортов/шифрования **не расширяется** сверх выбранного (D14): транспорты **tcp/raw, ws, xhttp**; security **tls, reality**; VLESS-шифрование **none и ML-KEM (`mlkem768x25519plus.*`)**. Внутри этого scope — **максимальная совместимость**: любая комбинация и любой параметр, которые Xray v26.10.10 поддерживает для этих транспортов/security/шифрования, принимаются и передаются в Xray через API (JSON → `infra/conf`, D19). В частности:
- REALITY с vision и без (пустой `flow`);
- ML-KEM, в т.ч. с `security=none` (шифрование делает VLESS) — комбинация выбранных значений, Xray её поддерживает;
- параметры выбранных security/транспортов: `spx`, `pqv`, `pcs`, `vcn`, `ech`, `fm` (finalmask), `alpn`, `fp`, `sni`, `host`, `path`, `headerType` (tcp), `mode`/`extra` (xhttp) и др. — всё, что Xray поддерживает для них;
- skip — только то, что Xray не принимает (`conf.Build` ошибка / живой Xray отклоняет), и транспорты вне scope (grpc, httpupgrade, kcp и т.п. → skip с причиной). Неизвестные параметры — игнорируются (D28).
Каждый поддерживаемый параметр покрывается live-тестом «дошёл до Xray через API».

## D29. Фильтры меток без lookahead: include/exclude-списки (2026-10-17)
Боевые конфиги владельца (`docker/scd/config.real-shape.yml`, `docker/sfc/config.real-shape.yml`) строят фильтры на lookahead (`(?!.*Extra)`, `(?=.*Extra)(?=.*WhiteList)`), которых нет в RE2 (D8). Чтобы выразить ту же логику на RE2:
- `labelIncludeRegex`: строка **или список** RE2-выражений — метка должна совпасть со **всеми** (AND);
- `labelExcludeRegex` (новое): строка **или список** — метка отбрасывается, если совпала **хотя бы с одним** (OR);
- оба необязательны (в sfc у output обязателен хотя бы один из двух); формат элемента — как в D8 (`/pattern/flags` или паттерн);
- lookahead/lookbehind в конфиге → ошибка `validate-config` с подсказкой переписать через `labelIncludeRegex`/`labelExcludeRegex`;
- применяется одинаково в scd (`subscriptions[].filters`) и sfc (`outputs[]`), общий код — `internal/common`.
Переписанные боевые фильтры (эквивалентны TS):
| Было (TS) | Стало (Go) |
|---|---|
| `/^(?!.*Extra)(?!.*WhiteList).*$/i` | `labelExcludeRegex: '/Extra\|WhiteList/i'` |
| `/^(?=.*Extra)(?!.*WhiteList).*$/i` | `labelIncludeRegex: '/Extra/i'` + `labelExcludeRegex: '/WhiteList/i'` |
| `/(?=.*Extra)(?=.*WhiteList)/i` | `labelIncludeRegex: ['/Extra/i', '/WhiteList/i']` |
Эквивалентность проверяется тестом на корпусе меток: решения TS-регулярок (эталон этапа 0) == решения Go include/exclude.
